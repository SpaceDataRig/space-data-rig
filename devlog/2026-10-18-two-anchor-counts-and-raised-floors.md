AUDIT PASS 6: THE COUNT WAS RIGHT. THE LABEL UNDER IT WAS NOT.

The board showed a tile reading 7 next to the word "on-chain", while the project's own ledger endpoint listed 18 anchored rows. Both numbers were true. Neither was the other. One field was answering two questions, and the label underneath it answered the one that number does not.

WHAT EACH NUMBER ACTUALLY COUNTS. The small one counts records whose CURRENTLY PUBLISHED bytes still match a landed transaction -- the property a provenance claim needs, because it means the file you can download now is the file the commitment covers. The large one counts transactions that exist and anybody can look up, regardless of whether the bytes on the site have moved on since. A bundle hash folds the timestamp of the run that produced it, so when the rotating survey re-measures a host, that record acquires a hash the chain never saw, the stale stamp is dropped rather than inherited, and the small number falls. Nothing was un-anchored. Eleven records were in that state when this was found. The reading taken for the figure below has the split at 12 matching and 7 superseded against a total of 19 -- which is exactly the point: the smaller figure moves continuously while the larger one stands, so the smaller one was never a total.

Both are published now, each carrying the question it answers: two named fields in the API with their definitions written where the code is read, two tiles on the board, two chips in the ticker.

FOLLOWING THAT DISCREPANCY FOUND SOMETHING WORSE THAN A MISLABELLED NUMBER. The ledger keeps one row per record, and both runtimes used to store whatever the newest attempt produced. A FAILED retry of an already-anchored record therefore overwrote the signature, slot and explorer address of a transaction that is still live on mainnet: evidence destroyed by a transient RPC error, and the cumulative count falling on a network hiccup. The fix is one rule, called by both runtimes: a row that landed keeps its proof, the failed attempt is recorded beside it in fields that describe the attempt rather than the row, and a genuinely newer transaction that succeeds still replaces it, as it should. The anchoring command line held a third, looser copy of the same count -- status alone, ignoring whether a lookup address exists -- and wrote its snapshot before reading the ledger, freezing whatever total an earlier run had left behind. Both corrected.

MEASURED, NOT ASSERTED. A new panel is generated from production rather than drawn from prose: it reads the state and ledger endpoints, writes the rows it read alongside both published counters, and REFUSES to draw when the counters do not follow from the rows -- three separate refusals, each with its own test. This pass' reading: 19 commitments, 12 whose published bytes still match, 7 superseded by a re-derivation, 0 anomalies. The drawing code is a pure function of that record file, no network and no clock, so the test suite rebuilds the shipped image from the shipped data and requires it byte for byte. A number inside a picture carries the authority of a number in a table and none of the same friction; that is why the picture gets the strictest of the three checks.

ONE DECISION TAKEN RATHER THAN ASKED. The suite's own floors had become permissions. Coverage gate raised from 85/75 percent (lines/branches) to 90/78 against a measured 95.7/82.5, and the floor on how many test files the runner must find raised from 60 to 90 against a measured 98. A floor that stays where it is while the number above it climbs for six audit passes is not a gate -- the old one would have waved through the loss of a third of the suite. Continuous integration is green on the new floors, which is the part that makes it a gate and not an intention.

A GALLERY GAP THAT ONLY SHOWED UP WHILE REGISTERING THE PANEL. The dashboard's figure gallery builds its cards from a committed manifest, and that manifest had not been regenerated since the last pass' figure was added. The figure was reachable and had been cited publicly; the page a reader goes to for every figure did not list it. A served file and an inventoried file are two different claims. Regenerated to 26 entries, and pinned by a test that fails if any served figure is missing from the manifest, if a card points at a file that is not there, or if a declared count disagrees with the list it declares -- the same shape of gate the report library got for the same reason.
